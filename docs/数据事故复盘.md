# v1.4.0 数据覆盖事故复盘

记录于 2026-11-23，v1.6.0 发布时。

## 发生了什么

v1.4.0 发布时，一份开发环境的数据库快照被上传并覆盖到线上，原有的学习记录随之丢失。

## 排查过程

对线上运行环境做过一次只读排查：列出沙箱内所有 SQLite 文件，逐个查询账号表，确认哪一份是覆盖前的真实用户库。

| 文件 | 修改时间 | 账号数 | 是否含主账号 |
| :--- | :--- | --: | :--- |
| `/workspace/users.db` | 11-23 09:44 | 47 | 否，这就是被覆盖上去的开发快照 |
| `/workspace/.workbuddy/holdover/parts-20261122c/users.db` | 11-22 10:53 | 47 | 否，是更早的一份快照 |
| `/workspace/data/users.db` | 11-23 10:05 | 48 | 是，但只有重建后的空账号，0 条记录 |

## 结论

三份库里，47 个账号全部是开发期的游客账号和测试账号。被覆盖之前的线上库没有任何副本留存，**原学习记录无法找回**。

主账号已经重建，可以正常登录，但历史进度是新的。

## 后续处理

v1.6.0 加了三层防护，目标是同样的事再发生时至少有退路：

1. 服务端每 30 分钟检查一次，库有变化就写全库快照，保留 20 份。即使再次被覆盖，覆盖前的那份一定在旁边。
2. 设置页可以导出和导入个人数据，用户自己手里也能留一份。
3. 项目根目录残留的旧 `users.db` 在启动时自动移到 `data/backups/legacy-*.db`，避免它哪天又变回线上库。

v1.7.0 起进一步统一了备份目录，并把发布前的全库快照下载列为硬性门禁，见 [维护手册](维护手册.md)。
